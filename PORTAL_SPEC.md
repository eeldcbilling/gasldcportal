## 1. Background
- Current portal: Google Apps Script web app (screenshots seen 02-Nov-2026). Pages: Dashboard, Download Bill,
  Update Payment Info, Billing History, Raise Ticket, Admin Panel. Download is slow (it extracts pages from big
  scanned PDFs, 15-20 s). Dashboard showed 455 users, 98 payments logged.
- Round 1 offline tool (`E:\ldc bills\`, separate repo) produces one PDF per bill:
  `archive\<mmm-yy>\<Bill No.>_<short name>_<mmm>.<yy>.pdf` (cancelled: `cancelled_<Bill No.>_<mmm>.<yy>.pdf`).
  These files are what the portal serves.

## 2. Fixed decisions (owner, from Round 1 SPEC Part D)
- Stay on **Google Apps Script**; **dedicated Google account** for the portal only.
- **No Google Sheets** as database. Data = **JSON files on Drive** generated by the offline tool, read and
  cached by Apps Script.
- Bill PDFs uploaded to **Drive**; portal returns a direct link -> near-instant download.
- Consumer submissions: one small JSON file per submission in a Drive folder (Option A); Firebase Firestore
  free plan (no card) is a later option.
- **No credit card**. **No PIN/login** for consumers (public access as today).
- **Volume (owner, 02-Nov-2026): plan for a payment entry for every consumer every month = about 600 entries
  a month (about 7,200 a year).**
- **PDFs: reach Drive through the synced folder `E:\LDC Portal Data\` (section 7; replaced manual upload).**
- The current payment page shows all consumers' UTRs and amounts publicly (owner's decision; keep or change: [OPEN]).

## 3. Pages and features
Revised by the owner 02-Nov-2026 (built, see PROGRESS.md):
1. **Dashboard** - hero, current-month banner (bill / dispatch / due date from the export), 4 stat cards,
   billed-vs-reported chart (12 months), insights, quick cards, recent activity (masked), bill-months timeline.
2. **Download Bill** - only **entity name + month** (both searchable dropdowns); no month pre-selected (owner, 03-Nov-2026): bill details appear only
   after the consumer picks a month; all bill details shown, View /
   Download PDF. No Type or Entity-type input (Bill No. = invoice no., one PDF per bill).
3. **Update Payment** - pick entity -> **latest pending bill** card (view/download). Mode A: one payment against
   that bill. Mode B "Reconcile old bills": table of older bills, each ticked row has its own date / UTR / amount
   / remarks. Every payment is against **one bill**; same UTR may cover several bills; duplicate UTR + bill
   is saved with a warning (owner, 03-Nov-2026; was: blocked); if any row is wrong nothing is saved. Below: all submitted payments in a data table (select,
   sort, search, 10/20/30/all, column show/hide, CSV export).
4. **Billing History** - pick entity -> totals, bills table (details pop-up with PDF and the payments logged
   against that bill), table of that entity's logged payments.
5. **Raise Ticket** - category, entity, e-mail, message -> ticket reference. (not built yet)
6. **Admin Panel** - shown only when signed in as eeldcbilling@gmail.com (checked on the server for every admin
   call). Now: data folder setting, reload cache, rebuild payment index. Further features [OPEN].
- Public sees per payment: entity, bill no., dates, amount, **UTR last 4 characters**; remarks admin only.
- Bill PDFs stay private in Drive; the server sends the bytes to the browser (no public sharing links).
Planned in Part D but not yet selected: automatic "earlier outstanding" calculation, recovery/ageing views.

## 5. Development workflow (proposed - owner to confirm)
- **clasp** (Google's command-line tool for Apps Script): code lives in this folder under `src/`, edited in
  VS Code with Claude Code, kept in git; `clasp push` uploads it to the Apps Script project.
  - One-time: install Node.js LTS; `npm install -g @google/clasp`; enable "Google Apps Script API" at
    script.google.com/home/usersettings (dedicated account); `clasp login`; create or clone the project.
  - Daily: edit -> `clasp push` (or `clasp push --watch`) -> test on the **Test deployment** URL (`.../dev`,
    always runs the latest pushed code, only the owner can open it) -> when good, update the live deployment
    **with the same deployment ID** (`clasp deploy -i <deploymentId> -d "note"`) so the public URL never changes.
  - Rollback: redeploy an earlier version number. Exact clasp commands depend on the clasp version - check
    `clasp --help` at setup.
- Apps Script structure (HtmlService serves one page; CSS/JS are included as HTML partials):
  `Code.gs` (doGet, routing), `Data.gs` (read JSON from Drive + cache), `Payments.gs`, `Tickets.gs`,
  `index.html`, `css.html`, `js.html`. Browser calls server functions with `google.script.run`.
- Web app settings: Execute as **Me** (dedicated account), access **Anyone**.
- Speed: CacheService (max 100 KB per key, max 6 h) + split JSON per month/consumer so each piece fits;
  bill download = Drive file link, no page extraction on the server.

## 6. Database - options (decided 02-Nov-2026: JSON on Drive only, see section 8.1)
| Option | For | Against |
|---|---|---|
| **A. JSON files on Drive** (already decided for read data) | Free, no card, same account, owner can look at files, offline tool writes them, nothing new to learn | No real queries; many small files get slow to list; parallel writes need LockService |
| **B. Firebase Firestore, free Spark plan** | Real database, fast queries, safe parallel writes, free quota far above our size | New platform + service-account key in Apps Script; must confirm at setup that no card is asked |
| C. Supabase free | Real SQL | Pauses after 7 days idle (rejected in Round 1) |
| D. Apps Script Properties/Cache | Built in | Far too small (KB limits); cache is temporary |
| E. Google Sheets / Excel | Familiar | Excluded by owner (accidental edits) |

**Recommendation (to confirm):** hybrid, start simple.
- **Read data** (consumers, bills, invoice amounts, PDF file IDs): JSON on Drive, written only by the offline
  tool / admin, read-only for the portal. Source of truth stays the Excel + Round 1 tool.
- **Write data** (payments, tickets): Option A - one JSON file per submission (never overwritten) + one index
  JSON per month rebuilt under LockService for duplicate checks and listing. Volume: about 600 payments a month - so
  submissions go in **one Drive folder per month** (never one huge folder), and the monthly index (about 600
  rows, roughly 100-150 KB) is cached in pieces because one cache key holds at most 100 KB. If this proves
  slow in testing, move payments to Firestore (option B) - only `Payments.gs` changes.
- Keep the code behind small functions (`savePayment`, `listPayments`) so a move to Firestore later changes
  only `Payments.gs`.

## 7. Data flow (decided 02-Nov-2026: synced folder replaces manual upload)
Google Drive for desktop (account eeldcbilling@gmail.com, **Mirror** mode) syncs `E:\LDC Portal Data\` with Drive.
| Subfolder | Written by | Read by |
|---|---|---|
| `bills\<month>\` PDFs | Round 1 tool / owner (PC) | Portal |
| `data\` portal JSON (consumers, bills, amounts) | Round 1 tool export | Portal |
| `submissions\<month>\` payments, tickets | Portal only | Round 1 tool (reconciliation) |
| `submissions\old-portal\index.json` old portal payments | Portal only (Admin import, once) | Portal |
| `import\old-payments.json` | PC: `tools/convert_old_payments.py` | Portal (Admin import) |
Rules: each side writes only its own subfolders, never the other's (avoids Drive conflict copies). Portal finds
files by name/month folder, never by a stored file ID (local saves may recreate files with new IDs); it rescans a
month folder when it changes and caches name -> ID. Sync delay of minutes is accepted.
